# 开发经验

> 踩坑、社区经验、最佳实践。

## Electron 在中国网络的安装

- **坑**：直接 `npm install electron` 会从 GitHub releases 下 ~100MB 二进制，国内大概率超时，且 `npm install` 整体返回成功但 `dist/` 不存在（postinstall 静默失败）。
- **解法**：设 `ELECTRON_MIRROR=https://registry.npmmirror.com/-/binary/electron/` + `ELECTRON_CUSTOM_DIR={{ version }}`。
- **验证必做**：装完检查 `node_modules/electron/dist/Electron.app/Contents/MacOS/Electron` 是否存在，不能只看 npm 退出码。
- **排错**：`node node_modules/electron/install.js` 配 `export DEBUG='*'` 可看下载 URL。

## macOS Gatekeeper（.app 签名问题）

（打包阶段补充）未签名 .app 双击会被拦"已损坏/无法验证开发者"。
安装脚本核心一行：
```bash
xattr -dr com.apple.quarantine "/path/to/本地运行前端项目.app"
```

## Node 路径在 Electron 打包后

Electron 打包后没有系统 node，子进程 `npm run dev` 需要：
- 方案：用 Electron 自带的 node 跑用户项目的 node_modules 是不行的（版本/ABI 可能不一致）。
- 现实：要求用户机器装了 Node（dev 阶段合理）；打包发布版可在 app 内捆绑 node 或引导安装。
- MVP 假设开发机有 node，启动前探测 `node -v`，缺失则提示。

## 中文路径

参考 zeen-tools：HTTP 响应头统一 `charset=utf-8`，`decodeURIComponent` 处理 URL 编码。macOS Finder 选的目录可能含中文，全程用 UTF-8，不要做编码转换。

## 静态 server 不要 SPA fallback（除非确认是 SPA）

直接对每个 path 查文件存在性。SPA fallback 会让 `/m/case` 这种别名打不开真实 html。只有 vite/next 这种已知 SPA 项目才 fallback 到 index.html。

## 🔴 路径解析：必须读 <base href>，绝不猜测式 strip（血泪教训）

**踩坑经过**：真实静态项目 91% 的 html 用 `<base href="/mobile/">` 这类标签改写相对路径解析根。
浏览器据此把 `../css/x.css` 解析成 `/mobile/css/x.css`。
服务器最初对 `<base href>` 完全无感，靠"猜测式 prefix-strip"兜底，导致：

1. mobile 项目 `/mobile/css/...` 404 → 硬编码剥 `/mobile/`（V1）
2. seo 项目 `/seo/css/...` 404 → 改成通用逐级剥前缀（V2）
3. **V2 引入静默数据错误**：`/page/css/x.css`（不存在）会剥掉 page 命中根 `css/x.css`，
   返回**错误的文件内容还报 HTTP 200**——比 404 危险十倍（用户看不到坏）。

**正确做法（当前实现）**：
- 服务启动时 `scanBaseHrefs(root)` 扫所有 html 的 `<base href>`，收集 base 前缀集合
  （如 `/mobile/`、`/mobile/casePage/`、`/home/page/`），按长度降序排
- 请求进来 `mapByBaseHref`：精确匹配已知 base 前缀（最长优先），剥掉后映射到磁盘根
- 匹配不上就原样处理，找不到文件就老老实实 **404，绝不猜测**

对照 nginx：成熟静态服务器从不猜路径。子路径部署的正确方式是部署方显式声明
（nginx 的 `location /home/ { alias root/; }`），我们的 base-href 映射等价于这个，
只是"声明"从项目 html 里自动读出来。

## 🔴 测试方法：用真实项目快照，别造临时目录（血泪教训）

"造临时目录"的单元测试有根本缺陷：**测试代码 = 实现者对问题的理解**。
我不懂 `<base href>` 时，造的测试目录自然不含它，测试自然全过——但那是假绿。

正确做法：
- 纯逻辑（detector/store/logger）用临时目录单元测试 OK
- 路径解析、资源加载这种**必须用真实项目快照做 e2e**：
  `test/diag-real.js` 对真实项目起服务 → 抓目录页所有链接 → 逐页逐资源请求 →
  断言"404 率 < 阈值 且无错误文件命中"
- 加"错文件命中守卫"：造含同名文件的项目，断言不存在的路径返回 404 而非 200
  （`test/test-base-href.js` 的正确性守卫段就是干这个的）

## 打地鼠反模式

每次只修当前 bug + 加针对当前 bug 的测试，不回测真实项目 → 前一个修复的回归
永远等用户打脸才发现。改 preview-server/runner 后强制跑 `test/diag-real.js`。

## 已知坑清单（遇到路径类问题先查这里）

- `<base href>` 改写相对路径（最常见，91% 真实项目用）
- npm 吞掉 `--port`（必须用 `--` 分隔符转发给脚本）
- dev server 警告洪泛 IPC（sass/postcss/deprecation 要节流+折叠）
- JS 模板字符串 `${x.img}` 被正则误当 URL（diag 的假 404 来源）
